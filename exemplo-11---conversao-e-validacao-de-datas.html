    14. Exemplo 11 – Conversão e validação de datas

    O novo aplicativo apresenta a inserção de datas:

    • em [1], o formulário de inserção
    • em [2], a resposta retornada

    O funcionamento do aplicativo é semelhante ao da entrada de números inteiros; portanto, comentaremos apenas os pontos que diferem.

    14.1. O projeto NetBeans

    O projeto do NetBeans é o seguinte:

    • em [1], as visualizações do aplicativo
      • [Accueil.JSP]: a página inicial
      • [FormDate.JSP]: o formulário de preenchimento
      • [ConfirmationFormDate.JSP]: a página de confirmação
    • em [2], o arquivo de mensagens [messages.properties] e o arquivo de configuração principal do Struts
    • em [3]:
      • [FormDate.java]: a ação que exibe e processa o formulário
      • [FormDate-validation.xml]: as regras de validação da ação [FormDate]. Esse arquivo delega essas validações ao modelo.
      • [FormDateModel]: o modelo da ação [FormDate]
      • [ FormDateModel-validation.xml]: as regras de validação do modelo
      • [FormDateModel.properties]: o arquivo de mensagens do modelo
      • [example.xml]: arquivo de configuração secundário do Struts

    14.2. A configuração do projeto

    O projeto é configurado principalmente pelo seguinte arquivo [example.xml]:

    
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE struts PUBLIC
        "-//Apache Software Foundation//DTD Struts Configuration 2.0//EN"
        "http://struts.apache.org/dtds/struts-2.0.dtd">

<struts>
  <package name="example" namespace="/example" extends="struts-default">
    <action name="Accueil">
      <result name="success">/example/Accueil.JSP</result>
    </action>
    <action name="FormDate" class="example.FormDate">
      <result name="input">/example/FormDate.JSP</result>
      <result name="cancel" type="redirect">/example/Accueil.JSP</result>
      <result name="success">/example/ConfirmationFormDate.JSP</result>
    </action>
  </package>
</struts>

    Ele é semelhante ao que foi analisado para a entrada de números inteiros.

    A visualização [ConfirmationFormDate.JSP] limita-se a exibir o modelo [FormDateModel]. As linhas 47 a 49 mostram a exibição de uma data. Queremos que essa exibição leve em conta um formato de data. Para isso, utilizamos a tag <s:text>, que já havíamos usado até então para a internacionalização do aplicativo.

    Aqui, a chave de mensagem utilizada é date.format. Essa chave se encontra no arquivo [FormDateModel.properties]:

    
date.format={0,date,dd/MM/yyyy}

    O valor associado à chave não é, neste caso, uma mensagem, mas um formato de exibição:

    • 0 é um parâmetro que representa o valor a ser exibido. Neste caso, será o campo date5 do modelo.
    • date representa uma data. Anteriormente, tínhamos number para um número.
    • dd/MM/yyyy representa o formato da data. Aqui, queremos que ela tenha o formato dd/mm/aaaa. O formato Java adequado é dd/MM/yyyy (d: dia, M: mês, y: ano)

    A tag

    
<s:text name="date.format">
            <s:param value="date5"/>
</s:text>

    exibe a mensagem {0, data, dd/MM/aaaa}, em que o parâmetro date5 (linha 2) substituirá o parâmetro 0 do formato. Assim, o modelo date5 será exibido no formato dd/mm/aaaa.

    • A regra das linhas 57-69 verifica se o campo de entrada date5 é uma data válida <=20/06/2001 e >=18/05/2000.
    • A regra das linhas 71-80 verifica se o campo date6 está no formato de data dd/mm/aaaa.

    14.8. A ação [FormDate]

    A ação [FormDate] é a seguinte:

    
package example;

import com.opensymphony.xwork2.ActionSupport;
import com.opensymphony.xwork2.ModelDriven;
import java.text.SimpleDateFormat;
import java.util.Date;
import java.util.Map;
import org.apache.struts2.interceptor.SessionAware;
import org.apache.struts2.interceptor.validation.SkipValidation;

public class FormDate extends ActionSupport implements ModelDriven, SessionAware {

  // construtor sem parâmetros
  public FormDate() {
  }

  // modelo da ação
  public Object getModel() {
    if (session.get("model") == null) {
      session.put("model", new FormDateModel());
    }
    return session.get("model");
  }

  @SkipValidation
  public String clearModel() {
    // raz do modelo
    ((FormDateModel) getModel()).clearModel();
    // resultado
    return INPUT;
  }

  public String cancel() {
    // limpa-se o modelo
    ((FormDateModel) getModel()).clearModel();
    // resultado
    return "cancel";
  }
  // SessionAware
  Map<String, Object> session;

  public void setSession(Map<String, Object> session) {
    this.session = session;
  }

  // validação
  @Override
  public void validate() {
    // formatação das datas
    SimpleDateFormat formateurDate = new SimpleDateFormat("dd/MM/yyyy");
    formateurDate.setLenient(false);
    // a data1 inserida é válida?
    if (getFieldErrors().get("date1") == null) {
      // verificação da validade da data
      try {
        formateurDate.parse(((FormDateModel) getModel()).getDate1());
      } catch (Exception e) {
        addFieldError("date1", getText("date1.error"));
      }
    }
    // a data6 inserida é válida?
    if (getFieldErrors().get("date6") == null) {
      Date d = null;
      try {
        // verificação da validade da data
        d = formateurDate.parse(((FormDateModel) getModel()).getDate6());
        // verificação dos limites
        if (d.after(formateurDate.parse("20/06/2001")) || d.before(formateurDate.parse("18/05/2000"))) {
          addFieldError("date6", getText("date6.error"));
          return;
        }
      } catch (Exception e) {
        addFieldError("date6", getText("date6.error"));
        return;
      }
    }
  }
}

    A ação [FormDate] segue o mesmo modelo da ação [FormInt]. Comentaremos apenas o método validate. Vale lembrar que o método validate é executado após a análise do arquivo de validação [FormDateModel-validation.xml] e antes da execução do método execute.

    • O método validate completa a validação das datas dos métodos date1 e date6. O arquivo de validação [FormDateModel-validation.xml] havia verificado se as cadeias de caracteres inseridas tinham o formato de uma data. Verifica-se agora se essas são, de fato, datas válidas. Lembre-se também de que date1 e date6 eram os únicos dois campos do modelo que eram do tipo String.
    • linha 50: cria-se um formato de data dd/mm/aaaa para verificar se as cadeias desse tipo são, de fato, datas válidas.
    • linha 51: setLenient(false) permite evitar que a data inválida 32/01/2012 seja interpretada como a data válida 01/02/2012.
    • linha 53: o campo date1 só é validado se as validações anteriores não tiverem apresentado erros nesse campo.
    • linha 56: verifica-se se date1 é uma data válida no formato dd/mm/aaaa.
    • linha 58: caso contrário, atribui-se uma mensagem de erro ao campo date1.
    • linha 62: date6 só é validado se esse campo tiver sido aprovado nas validações anteriores.
    • linha 66: verifica-se se date6 é uma data válida
    • linha 68: se date6 for <18/05/2000 ou date6>20/06/2001, então date6 está incorreto.

    14.9. Últimos detalhes

    O formulário anterior apresenta falhas, conforme mostra o exemplo a seguir:

    • em [1], insere-se uma data inválida
    • em [2], ela foi aceita. Apenas os primeiros caracteres dd/mm/aaaa foram considerados.

    Os campos date2 a date5, que estão vinculados a modelos do tipo Date, apresentam esse problema. Mais uma vez, talvez eu tenha deixado passar alguma informação na documentação. Os campos date1 e date6, que estão vinculados a modelos do tipo String, não apresentam esse problema.
